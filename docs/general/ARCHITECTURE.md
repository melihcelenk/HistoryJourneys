# Architecture

History Journeys is a static web application: everything runs in the browser,
there is no server and no user data (decision D6). This document describes how
the code is organized and why.

## Overview

```
content/*.json ──(schema + consistency checks)──► scripts/build-db.ts ──► public/data/hj.sqlite
                                                                                 │
browser: sql.js ──► ContentRepository ──► store (Zustand) ──► game screen (React)
                                              │                  ├─ MapView: MapLibre | PixiJS
                                       route engine              └─ cards, chain, HUD, games
```

## Directories

| Directory | Contents |
|-----------|----------|
| `content/` | The content as reviewable files: one JSON file per figure, the lines, the relation types and the generation rule set (`content/rules/RULESET.md`). |
| `scripts/` | Build scripts: `build-db.ts` (content → SQLite), `build-geo.ts` (Natural Earth → map data), `verify-wikidata.ts` (checks years against Wikidata), `build-icons.py`. |
| `src/domain/` | Pure logic with no browser or framework dependency: content schema, route engine, journeys, calendar, link markup, quiz rounds. |
| `src/data/` | The database schema, the database builder, content validation and the repository that reads the database. |
| `src/app/` | Application state (`store.ts`), the URL mapping (`urlState.ts`) and the database loader. |
| `src/map/` | The `MapView` interface, the scene builder and the map renderers. |
| `src/ui/` | React components and the visual theme (`src/ui/theme/*.css`). |
| `tests/unit/` | Vitest tests of the domain, data, URL and scene logic. |
| `tests/e2e/` | Playwright tests on a desktop and a phone viewport; they save screenshots to `tmp/screens/`. |

## Key decisions

### Content is data in the repository

Cards are generated by an LLM under a written rule set and stored as JSON, so
that corrections can be proposed as pull requests. `npm run db:build` validates
every file against the schema (`src/domain/contentSchema.ts`) and the
cross-file rules (`src/data/contentValidation.ts`): relation targets, link
targets, cited sources, journey order, and one set of coordinates per place.
The build fails on any error, so broken content never reaches the application.

### The database sits behind a repository

The application reads content only through `ContentRepository`
(`src/data/ContentRepository.ts`). Today it is implemented with SQLite running
in the browser (sql.js); replacing it with an HTTP API later touches one file.

### The map sits behind an interface

Everything the map shows is computed by `buildScene` (`src/map/mapScene.ts`)
as plain data: city labels, journey stops, figures and paths. A renderer only
draws a scene. `MapLibreMapView` and `PixiMapView` implement the same `MapView`
interface (`src/map/MapView.ts`) and are loaded on demand.

The map uses no tile server. Land, lakes and rivers come from Natural Earth
(public domain), clipped to the region of the game and shipped with the
application. Place names come from our own content, so the map never shows
modern borders or labels, and the application works offline.

### Routes are computed from typed relations

`findRoutes` (`src/domain/routeEngine.ts`) builds a graph from the relations
and searches it once per kind of route (requirement FR-8):

- **Direct** ("Doğrudan"): only relations between people who had to do with
  each other (succession, family, service, teaching, conflict).
- **Influence** ("Etki"): influences are cheap and direct relations
  dear, so the route follows influences and may jump over centuries; it is
  offered only when it contains at least one influence.

Which relation type belongs to which kind is data (`mode` in
`content/relation-types.json`), as are the base weights. A step may not move
against the direction of time by more than a generation, which removes
meaningless shortcuts (requirement FR-12). The engine returns data only; the
names of the kinds are in `src/ui/routeLabels.ts`.

### The map shows only what is recorded

A figure is on the map only in the years of one of its journey stops
(`stopAtYear` in `src/domain/journey.ts`). In a year between two stops nothing
is known, so nothing is shown rather than a guess. The scene of a year
(`src/map/mapScene.ts`) holds the figures present that year with the trail
that led each of them there; the whole journey of the figure in focus is added
only when the reader switches it on.

Playback does not count years. `buildChronicle` (`src/domain/chronicle.ts`)
lists the journey stops of the route in order of time, and `usePlayback`
(`src/ui/usePlayback.ts`) steps through them: it moves time to the event, puts
it in the spotlight (the camera goes there and a caption tells what happened)
and rests for a time that depends on the chosen speed.

### State and links

All state lives in one Zustand store. The shareable part of it is mirrored to
the URL hash (`src/app/urlState.ts`), so every route, card, detour and year has
a stable link, and the same build works from any static host or from inside a
store package.

### Visual assets

The look (parchment, stone, brass, wax) is built from CSS and inline SVG; map
textures are generated on a canvas. No third-party image assets are used, so
there is nothing to license (requirement FR-33). Fonts are Cinzel and
EB Garamond (SIL Open Font License), bundled with the application.

## Focus and overview

The store has one notion of "the figure in front of the reader" (`activeFigureSlug`): the detour card, else the
open route card. On a route with no card open there is none; this is the overview.

| | A card is open | Overview |
|---|---|---|
| Timeline and playback | the life and the stops of that figure | all figures on the route |
| Map | the journey of the figure, one group of eight stops (`JOURNEY_GROUP_SIZE`) | figures of the year with their trails |
| Link | `k=<figure>` | `g=1` |

The group that is shown follows the reader (`journeyPosition`): the stop being told about, else the stop of the
year, else the last one reached. Trails are cut to the same groups. The switches for the journey and the lines are
on by default and are written to the link only when off (`j=0`, `l=0`). The kind of route the reader chose
(`routeKind`) is kept apart from the route that is open, because the chosen kind may not exist between two figures.

Opening a figure moves time to the first stop of its journey (`startOf`). Cards load after the route is known, so
until the card arrives time waits at the birth year and the figure is remembered in `awaitingStart`; when the card
arrives time moves on, unless the reader has chosen a year meanwhile or the figure is no longer open. A year in a
link always wins. `activeYear` only orders figures in time for the games.

## Portraits

A figure may have a `portrait` record in its content file: the file on Wikimedia Commons, its page, the work, its
maker, its date, its licence, whether it was made in the lifetime of the figure, and the square to cut out for the
medallion. The schema accepts only the licences in `PORTRAIT_LICENSES` (public domain and CC0); which pictures qualify
is decided by the rules in `content/rules/RULESET.md`, section 8, and recorded in `content/portraits/REVIEW.md`.

`scripts/build-portraits.py` fetches the pictures, crops them and writes `public/portraits/<slug>.webp`. The images
are committed and cached by the service worker: the application never asks another server for a picture. The record,
without the crop, travels through the database (`figure.portrait_json`) to `FigureSummary.portrait`; `Medallion` shows
the picture when there is a record and falls back to the emblem of the kind when there is none or the image fails.


## 3D scene: performance rules

The scene (`sahne.html`, `src/scene3d/`) must stay fluid on an integrated graphics card. These rules came out of
measuring it (HJ-2, phase 6: 12–24 frames a second before, 56–60 after, on Intel Arc at 1920×1080).

- **Separate in the source, one object in the output.** Whatever lies on one surface is painted into one texture
  and drawn as one mesh. The map on the table is the example: its coasts, signs, names and marks are separate
  functions and data, and one picture on one sheet.
- **No texture is painted or uploaded every frame.** A picture is sent to the graphics card again only when what
  it shows changes (`MapBoard.show`).
- **Shadows of things that do not move are drawn once.** The scene turns the automatic update of the shadow map
  off when it is complete.
- **Layered effects are kept as small as they can be.** Shells of hair, samples of anti-aliasing and the size of
  the bloom are costs paid on every pixel they cover.
- **Measure, do not guess.** `npx tsx scripts/dev/measure-scene.ts` times the frames on the real graphics card, at
  the door, at the table and during the briefing. Read the mean frame time, not the median; write the numbers
  before and after into the phase document.
- **A weak graphics card gets fewer pixels, not fewer frames.** `dynamicResolution.ts` lowers the fineness of the
  picture step by step when frames are slow.
- **The drawing budget is tested.** `tests/e2e/scene.spec.ts` fails when a frame needs more draw calls or
  triangles than the budget allows.

## 3D scene: sound

- **One switch.** `audio/soundStage.ts` owns everything that sounds: the narrator, the sound of the room and the
  button (and the M key) that turns both off. The choice is kept in the browser's storage.
- **Sound starts with the first thing the player presses**, as browsers require, and stops while the page is in
  the background.
- **The narrator speaks a step from its recording if the step names one (`audio` in `content/scenes/*.json`),
  otherwise with the Turkish voice of the device.** No sound file is shipped today; which source becomes the
  permanent one is an open decision (HJ-2, S1). Free Turkish voice models were ruled out: their licences forbid
  commercial use.
- **The words are always on the screen too.** Sound is never the only carrier of information.
- **The sound of the room is generated** (`audio/ambience.ts`), not recorded; its level follows the distance to
  the hearth and drops while the figure speaks (`audio/ambienceLevel.ts`).
- **A test cannot listen.** The tests check what is handed to the device (text, voice, rate, pitch) and the level
  of the generated sound. Whether it sounds right has to be judged by ear.
